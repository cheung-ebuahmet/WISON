# CONSTITUTION — AI_Knowledge 知识库宪法 / The Constitution

> **地位 / Supremacy.** 本文件是 AI_Knowledge 的最高约束。`00_Glossary`–`08_Prompts` 下一切实体、规则、关系、案例、提示词，凡与本宪法冲突者，**以本宪法为准**。
> **宗旨 / Purpose.** 我们不是在建资料库，而是在训练一位**资深 ADNOC EPC 合同专家**。每一条内容的价值标准只有一个：它是否让这位专家更强。

---

## 第一条 · Single Source of Truth（单一事实源）
- **原则**：任何一个事实只在一处权威记录，其余位置一律**引用**，不复制。
- **为什么**：复制即分叉。合同金额抄三遍，改一遍就有两处是错的，AI 会自信地援引错误值。
- **如何执行**：事实归其主对象（如 LD 只写在该 `Contract` 对象里）；别处需要时写 `见 Contract-<编号>#LD`，不重抄数值。
- **违反示例**：在 `03_Rules` 里又写死"LD = 每天 X"。→ 应引用实体字段。

## 第二条 · Every Rule Has Evidence（规则必有证据）
- **原则**：每条规则/结论必须能追溯到 **合同条款 / 规范 / 邮件 / 会议纪要 / 案例** 之一。
- **为什么**：无证据的规则是臆断；专家的每句话都要能被质证。
- **如何执行**：规则末尾强制 `依据：<出处 + 条款号>`；暂无证据的标 `[未核实]`，**不得进入正式库**，只能待验证。
- **违反示例**：`IF 无 Instruction THEN 不能付款`（无出处）→ 标 `[未核实]` 直到绑定条款。

## 第三条 · Facts ≠ Knowledge ≠ Reasoning（事实 / 知识 / 推理，严格分层）
- **原则**：三者物理分离，永不混写。
  - **Facts 事实** = 原始资料（`Main_Contract` 等，只读）。
  - **Knowledge 知识** = 从事实提炼的对象/规则/关系（本目录）。
  - **Reasoning 推理** = 运行时由 Copilot 现场产生（`08_Prompts` 定义其方式）。
- **为什么**：把推理当事实存，错误会被当真相反复引用，污染整个系统。
- **如何执行**：知识层每条注明它来自哪个事实；推理结论若要固化，须降格为"案例/QA"并重新标注证据与把握度。

## 第四条 · Objects Before Documents（对象先于文件）
- **原则**：先有知识对象，再谈它出自哪份文件。文件是对象某字段的**出处**，不是知识本身。
- **为什么**：AI 学的是 `Contract / Variation / Clause` 对象，不是"第 37 页那段 PDF"。
- **如何执行**：任何新资料进来，先问"它实例化/更新了哪个对象的哪个字段？"，再登记出处路径。

## 第五条 · Relations Are First-Class Citizens（关系是一等公民）
- **原则**：实体之间的关系（`governs / flows-down / affects / depends-on …`）与实体本身同等重要，单独建、单独维护。
- **为什么**：能推理的系统靠的是关系图，不是孤立卡片。Back-to-Back 分析本质就是查 `flows-down` 边的断点。
- **如何执行**：关系写进 `02_Relationships`，格式可解析：`<源> <关系> <目标> [条件] [出处]`。

## 第六条 · Version Everything（一切留版本）
- **原则**：合同修订（Amendment）、规则变化、案例结论一律**留版本，不覆盖历史**。
- **为什么**：合同的价值在上下文——红线版、IFA/IFC、旧结论都是证据链。覆盖 = 毁证。
- **如何执行**：依赖 `D:\Wison` 的 git 保留历史；对象内用 `supersedes` 关系指向被取代版本，而非删除旧值。删除动作一律送回收站，绝不永久删。

## 第七条 · Separate Normative vs Practical（规范知识 vs 实践知识，分离并存）
- **原则**：区分"**合同要求**"（Normative，白纸黑字）与"**项目实际做法**"（Practical，现场惯例），两者都保留，各自标来源。
- **为什么**：合同写 28 天，现场按 14 天——两者都真、都要知道。合同给 What，实践给 Why。这正是专家访谈（Phase 4）要灌入的隐性知识。
- **如何执行**：字段/规则标 `[Normative]` 或 `[Practical]`；实践知识必须注明来源（谁说的/哪次会议/哪个案例），并可与规范值并列对照。

## 第八条 · Canonical Before Instance（先规范，后实例）
- **原则**：任何项目知识都应先归入稳定的**通用模型（Canonical）**，再通过 **Project Profile** 实例化。项目差异应尽量体现在 Profile，而不是修改 Ontology 或核心实体定义。只有当**多个项目**都无法表达某类概念时，才考虑调整 Canonical 模型。
- **适用范围**：不止本体（Ontology），涵盖 Entities / Relationships / Rules / Processes 整个知识体系。
- **为什么**：把项目特例焊进通用模型，换个 ADNOC 项目（气处理/海上/炼厂）就得重构；差异下沉到 Profile，模型才耐用。
- **如何执行**：通用结构进 `ONTOLOGY.md` 与 `01_Entities/*.md`；项目取值进 `PROFILE.md`。改 Canonical 前先自问"是否只有这一个项目需要？"——是则放 Profile。
- **违反示例**：把"液硫造粒项目的 PAC 定义"写进 Contract 实体 → 应写进 Profile；本体只保留"完工里程碑"这一通用槽。

### 附则 / Amendment
- 本宪法可修订，但修订本身遵守第六条（留版本）。
- 与全局工作规范（命名协议、删除送回收站、文件归位）一致；冲突时，涉及**知识建模**以本宪法为准，涉及**磁盘/文件操作**以全局规范为准。
- 每新增一条规则或实体，回看：是否违反上述八条？违反则先改结构，再填内容。
